# PBI 501.007: Orient in one GitHub request

**Priority:** P3
**Dependencies:** PBI 002.003

## Description

Orient (PBI 001.001) reads GitHub through several REST calls in three parallel stages: list feature branches, then state and tree and PR, then ADR header and review header and checks. About a second per call from a Vercel function, which is inaudible from CV, so REST was chosen to keep the first version simple. GitHub's GraphQL API can answer the same questions in one request, because a commit can be asked for a file by path and a nested tree inside the same query as the branch list and its pull requests. This slice replaces the staged REST reads with one snapshot query plus one batched body query, keeping the derivation record and its tests unchanged. Reopen when orient latency is noticeable from CV, or when later phases push the REST call count up.

Traces to ADR 001.001 decision 4 and Architecture decision 1 (GitHub is the truth).

## Deliverables

- Orient obtains every fact the derivation needs in at most two GitHub round trips: one snapshot covering feature branches, state, the `.wag/` listing, the pull request and its check rollup; then one batched read of the file bodies the snapshot said to read.
- The derivation record, its rules and its unit tests are unchanged; only the GitHub module's read path differs.
- The snapshot response is validated at the boundary by one schema, per the Architecture validation policy.
- The GitHub module stays free of phase knowledge: the branch prefix, directory and depth are arguments the engine supplies.

## Acceptance Criteria

- [ ] An orient on a project with a feature branch, open PR and review file completes with exactly two GitHub requests, verified by request logging in tests.
- [ ] Every position in ADR 001.001's derivation table reports the same phase and position before and after the change, verified by the existing derivation tests running against both read paths.
- [ ] A snapshot response that fails validation produces a refusal naming the field, never a default.
- [ ] Orient latency measured from the live endpoint is lower than the REST path on the same project.

## Testing Requirements

- [ ] Recorded-fixture tests for the snapshot and body queries, valid and malformed.
- [ ] The full derivation suite run against the GraphQL read path.
- [ ] A latency comparison against the REST path on this repo, recorded in the PR.

## Technical Notes

Octokit already exposes `graphql`; no new dependency. The tree nesting in the query is fixed to the depth `.wag/` actually has, four levels for the completed mirror. GraphQL rate limiting is points-based and a query of this size costs one or two points against five thousand an hour. A tarball download was rejected in the ADR grill: one call, but it ships the whole repo and needs untarring inside the function.
