# PBI 001.012: Adopt an existing wag2 project

**Priority:** P1
**Dependencies:** PBI 001.005

## Description

Sam's existing wag2 projects (wag3, radd, gigger, vorsann, cmn-payonward-portal, and this repo) were not generated from the template repo, so they lack what wagc needs to run them: the workflow file, the subscription token secret, and a registration with the server. This slice delivers adoption as a ritual: orient on a project name the server does not know offers discovery or adoption; adoption names an existing repo that already holds `.wag/`, walks the steps, and approve commits the workflow and registers the project. After adoption an existing project is not a special case; every other PBI treats it like one born from the template. State needs nothing added, because the phase is derived from the artifacts (Architecture decision 7), so a project worked from CC and CV in turn never disagrees with itself.

Traces to PRD v1 scope "adopt existing wag2 projects" and Architecture decision 7.

## Deliverables

- Orient on a project name the server does not know offers discovery or adoption; naming an existing repo that holds `.wag/` returns the adoption ritual instead of refusing.
- Approve in the adoption position checks: the repo is private on GitHub, the backlog uses per-epic numbering (a legacy backlog refuses and names the migration step to run from CC first), the state file validates, and no open snags.
- A passing approve, in one commit on dev: commits the workflow file with the pinned toolkit ref, and registers the project name against the repo with the server.
- The ritual tells Sam to add the subscription token secret to the repo, and approve verifies the secret exists before finishing; the ADR decides whether the server can set it from a server-held copy instead.

## Acceptance Criteria

- [ ] From CV, orienting on one of the five existing projects, pushed to GitHub as private, reports it as adoptable with the steps.
- [ ] Approving adoption results in the workflow file committed on dev and the project known to the server, in one commit, with state unchanged.
- [ ] Orient immediately after adoption reports the project's true position: an approved ADR with no PR is reported as dev, a project between PBIs as adr.
- [ ] Approving adoption on a public repo refuses and says why.
- [ ] Approving adoption on a legacy-numbered backlog refuses and names the migration command.
- [ ] Approving adoption with the secret missing refuses and names the secret.
- [ ] After a CC session approves an ADR on an adopted project, the next orient from CV reports dev with no adoption step repeated.
- [ ] A dev run dispatched on an adopted project completes to a PR exactly as on a template-born project.

## Testing Requirements

- [ ] Unit tests for adoptable detection and each adoption check.
- [ ] Integration test: adopt a throwaway copy of an existing project's `.wag/` tree, then orient and dispatch.
- [ ] Negative tests: public repo, legacy backlog, missing secret.

## Technical Notes

Legacy backlog migration stays a CC command because it renumbers freely and is one-time. The project registry is server-owned state from PBI 001.001 and gains entries here as at init.
