# PBI 001.012: Adopt an existing wag2 project

**Priority:** P1
**Dependencies:** PBI 001.005

## Description

Sam's existing wag2 projects (wag3, radd, gigger, vorsann, cmn-payonward-portal, and this repo) were not generated from the template repo, so they lack what wagc needs to run them: a phase in state, the workflow file, the subscription token secret, and a registration with the server. This slice delivers adoption as a ritual: orient on a project name that maps to a repo with `.wag/` but no wagc stamp reports it as adoptable, walks the steps, and approve stamps, commits and registers it. After adoption an existing project is not a special case; every other PBI treats it like one born from the template. It also fixes the rule for a project worked from both CC and CV: what orient does when the stored phase disagrees with the derived position.

Traces to PRD v1 scope "adopt existing wag2 projects", Architecture decision 7 and open question 9.

## Deliverables

- Orient on a repo that has `.wag/` and no phase field reports the project as adoptable and returns the adoption ritual instead of refusing.
- Approve in the adoption position checks: the repo is private on GitHub, the backlog uses per-epic numbering (a legacy backlog refuses and names the migration step to run from CC first), the state file validates apart from the missing phase, and no open snags.
- A passing approve, in one commit on dev: writes the phase derived from the artifacts into state, commits the workflow file with the pinned toolkit ref, and registers the project name against the repo with the server.
- The ritual tells Sam to add the subscription token secret to the repo, and approve verifies the secret exists before finishing; the ADR decides whether the server can set it from a server-held copy instead.
- Orient on any project whose stored phase disagrees with the derived position reports the disagreement and, per the rule the ADR fixes, either repairs the phase or refuses until it is repaired. The rule is the same for adopted and template-born projects.

## Acceptance Criteria

- [ ] From CV, orienting on one of the five existing projects, pushed to GitHub as private, reports it as adoptable with the steps.
- [ ] Approving adoption results in state carrying a correct phase, the workflow file committed on dev, and the project known to the server, in one commit.
- [ ] Orient immediately after adoption reports the project's true position: an approved ADR with no PR is reported as dev, a project between PBIs as adr.
- [ ] Approving adoption on a public repo refuses and says why.
- [ ] Approving adoption on a legacy-numbered backlog refuses and names the migration command.
- [ ] Approving adoption with the secret missing refuses and names the secret.
- [ ] After a CC session approves an ADR without writing the phase, the next orient from CV reports the mismatch and resolves it per the fixed rule rather than acting on the stale phase.
- [ ] A dev run dispatched on an adopted project completes to a PR exactly as on a template-born project.

## Testing Requirements

- [ ] Unit tests for adoptable detection, each adoption check, and phase derivation from artifact combinations.
- [ ] Unit tests for the stored-versus-derived mismatch rule.
- [ ] Integration test: adopt a throwaway copy of an existing project's `.wag/` tree, then orient and dispatch.
- [ ] Negative tests: public repo, legacy backlog, missing secret.

## Technical Notes

The uphill fix is for wag2 in claude-home to write the phase at the same continuation boundaries wagc does, so CC and CV sessions stop disagreeing at the source; that change lives outside this repo and is a global disposition. Until it lands, the mismatch rule carries the load. Legacy backlog migration stays a CC command because it renumbers freely and is one-time.
