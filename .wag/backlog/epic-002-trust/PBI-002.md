# PBI 002.002: Permission boundary on what CV may do

**Priority:** P2
**Dependencies:** PBI 002.001

## Description

The server decides what CV may do, not CV. This slice delivers a permission boundary enforced server-side: which projects a caller may touch, which continuations are allowed in which phases, and which actions need an explicit confirmation carried in the payload (merge, override, repo creation). A call outside the boundary is refused with a reason and logged. This is the first place multi-caller identity could later attach, but v1 has one caller and one shared secret.

Traces to PRD Epic 002, Architecture decision 11.

## Deliverables

- A declared boundary the server reads at startup: allowed projects, allowed continuations per phase, and the set of actions that require an explicit confirmation in the payload.
- Every call is checked against the boundary before any module runs; a refusal names the rule.
- Confirmation-required actions (merge, override of a failed check, repo creation, epic close) proceed only when the payload carries the confirmation, and the ritual tells CV to obtain it from Sam aloud.
- Refusals are logged by PBI 002.001's writer with the rule that refused.
- Changing the boundary is a deploy, not a call; the surface cannot widen its own permissions.

## Acceptance Criteria

- [ ] A call on a project outside the allowed set refuses and names the rule.
- [ ] Approving merge without the confirmation in the payload refuses and the ritual asks CV to confirm with Sam; with it, proceeds.
- [ ] A continuation not allowed in the current phase refuses.
- [ ] Every refusal appears in the audit log with its rule.
- [ ] No call can alter the boundary.

## Testing Requirements

- [ ] Unit tests for each rule type: project, phase-continuation, confirmation.
- [ ] Integration test: a refused merge and an accepted merge, both logged.
- [ ] Negative test: a payload attempting to carry boundary changes is ignored and logged.
